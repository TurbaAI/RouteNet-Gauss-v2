# `mawi_pcaps` — dataset reference

> **Note:** This file was written by Claude Code as a data-exploration aid. It is **not** part of
> the original RouteNet-Gauss paper release. Everything below was derived from the dataset's own
> `dataset_spec.pb` field list, from how `models.py` consumes each tensor, and from the repository
> README — not from external assumptions about the MAWI archive. The worked-examples section at the
> bottom is generated from the real data by
> `python -m visualization.describe_dataset --update-readme`.

## What this dataset is

`mawi_pcaps` is the dataset the paper calls **"Real-World Packet Traces"** (RouteNet-Gauss:
*Hardware-Enhanced Network Modeling with Machine Learning*, IEEE ToN 2026,
[DOI](https://doi.org/10.1109/TON.2026.3668972)). Real packet traces drive a hardware testbed,
which acts as an accelerator to produce training data with real-world fidelity — as opposed to
`trex_*`, which is generated by the TREX traffic generator, and `mawi_pcaps_simulated`, which is
the same scenarios re-run through the OMNeT++ discrete-event simulator.

| partition | shards | size |
|---|---|---|
| `training` | 9 | 846 MB |
| `validation` | 2 | 175 MB |
| `test` | 1 | 84 MB |

Load it only via `utils.load_dataset("mawi_pcaps/test")` — it concatenates the numbered shards.
Each element is a `(features, label)` pair; `features` is a dict of **56 named tensors**.

## Timestamps: there are none

**The dataset contains no wall-clock time information of any kind.** Grepping the complete field
list for `time|stamp|date|epoch|clock|duration|window` returns nothing. So:

- there is **no capture date/time**, no start time, no per-packet or per-window timestamp;
- you cannot place a sample on a real calendar, or order two samples in real time, from the data
  alone;
- what *does* exist is **relative** temporal structure: each sample is divided into `seg_num`
  consecutive aggregation windows (the paper's TAPE — Temporal Aggregated Performance Estimation).

## Temporal granularity

Per-window quantities are shaped `(num_flows, seg_num, 1)` — one value per flow per window — and
`flow_trans_pkts_per_seg`, `loss_rate_per_seg`, and `flow_seg_membership` are explicitly per-window.
The repository README says only that TAPE offers "configurable temporal granularity"; **the window
duration is never stated, and is not stored as a field.**

There is exactly one lever for recovering it. `mawi_pcaps` is the **only** dataset in this repo that
carries `flow_packets_per_ms` (see the comparison below), and its **structure** is what measures
granularity.

Layouts measured from a real sample (`sample_idx=2003`: 31 flows, 40 windows):

| field | measured layout | notes |
|---|---|---|
| `flow_packets` | `(31, 40, 1)` dense | **flow-major** — one scalar per flow per window |
| `flow_packets_per_ms` | `(31, 40, ragged[100..7434], 1)` | **also flow-major**, with a variable-length series per (flow, window) plus a trailing singleton axis |

**Conclusion: the absolute window duration is not derivable from this dataset.** `seg_num` fixes how
*many* windows a sample has (40 in that sample); nothing fixes how *long* one is. The
`flow_packets_per_ms` series length varies ~74× between (flow, window) pairs (100 to 7434 entries),
so it cannot be "milliseconds per window" when the windows are equal in count — it behaves like a
per-flow variable-length series whose unit is undocumented.

`visualization/report.py`'s `window_duration_ms()` reports this, printing both measured layouts so
the reasoning is checkable, under `-- Temporal structure & granularity --` in every `summary.txt`.

> **Two corrections to earlier versions of this file**, recorded so the approaches aren't retried:
> 1. Dividing `flow_packets` by `flow_packets_per_ms` and reading the ratio. Wrong — the fields
>    differ in rank, so they are not element-wise comparable, and the division crashed on the
>    ragged axis.
> 2. Describing `flow_packets_per_ms` as **segment-major**. Wrong — measurement shows `dim0 = flows`
>    and `dim1 = windows`, the same order as `flow_packets`. The earlier inference came from a crash
>    traceback showing `(20, 40)`, where 20 was that sample's *flow* count, not a window count.
>
> A related bug was fixed at the same time: reading the *deepest* nested length measured the trailing
> singleton axis and reported a bogus "window spans ~1 ms".

## Field reference

56 fields. `models.py` reads only **18** of them (the `used by model` column) — the remaining **38**
carry information the model never sees, which is where most of the "extra" signal lives.

### Topology & routing (index tensors, mostly ragged)

| field | used by model | meaning |
|---|---|---|
| `link_to_path` | yes | Per flow, the **ordered** sequence of link ids it traverses. The routing table, and the only source of path structure. |
| `path_to_link` | yes | Per link, the flows crossing it (flow index in column 0). The inverse mapping. |
| `queue_to_link` | yes | Per link, the queue(s) feeding its transmit side. |
| `node_groupings` | yes | Per node, the queues it owns. |
| `node_groupings_inversed` | yes | Per queue, the owning node. Combined with the two above this is what lets the topology be reconstructed (there is **no** explicit edge list). |
| `routers_groupings`, `routers_groupings_inversed` | — | Same mapping restricted to routers. |
| `switches_groupings`, `switches_groupings_inversed` | — | Same, restricted to switches. |
| `path_to_r_link`, `path_to_s_link` | — | Per-tier variants of `path_to_link`. |
| `r_queue_to_r_link`, `s_queue_to_s_link` | — | Per-tier variants of `queue_to_link`. |

### Link properties

| field | used by model | meaning |
|---|---|---|
| `link_capacity` | yes | Link capacity in **Gbps** (`models.py` multiplies by `1e9` to get bit/s). |
| `link_pkt_header_size` | yes | L1/L2 framing overhead in bytes added per packet, folded into the load calculation. |
| `link_r_capacity`, `link_s_capacity` | yes | Per-tier capacities, used when the unified `link_capacity` is absent. |
| `link_r_pkt_header_size`, `link_s_pkt_header_size` | yes | Per-tier header sizes, same fallback. |
| `buffer_type` | yes | Per **queue**, a categorical buffer/scheduling class in `{0,1,2}` (`max_buffer_types = 3`). This is the *only* queue-configuration field — there is no continuous buffer-size field. |

### Per-flow traffic inputs

| field | used by model | meaning |
|---|---|---|
| `flow_traffic` | yes | Offered traffic per flow per window. z-score normalised inside the model. |
| `flow_packets` | yes | Packet rate per flow per window. Also z-score normalised. |
| `flow_packet_size` | yes | Mean packet size; used for the transmission-delay term when `use_trans_delay=True`. |
| `flow_has_traffic` | yes | Boolean mask: did this flow send anything in this window. |
| `flow_length` | yes | Number of hops in the flow's path. The model treats this as the authority on path length. |
| `flow_packets_per_ms` | — | **`mawi_pcaps`-only.** A variable-length *series* per (flow, window), not one scalar: measured layout `(flows, windows, ragged[100..7434], 1)`. Its unit is undocumented — see the granularity section. |
| `flow_id` | — | Flow identifier. |
| `flow_seg_membership` | — | Which temporal window(s) a flow belongs to. |
| `seg_num` | yes | Number of temporal windows in this sample. |

### Per-flow performance targets (what is predicted)

| field | used by model | meaning |
|---|---|---|
| `flow_avg_delay`, `flow_p50_delay`, `flow_p75_delay`, `flow_p90_delay`, `flow_p95_delay`, `flow_p99_delay`, `flow_max_delay` | — (labels) | Per-flow per-window delay: mean, percentiles, maximum. `train.py` selects avg + p50/p90/p95/p99 as its five targets; **`p75` and `max` are available but unused** by the shipped config. |
| `flow_avg_jitter` … `flow_p99_jitter`, `flow_max_jitter` | — (labels) | The same family for jitter, selectable by setting `target = "jitter"`. |
| `flow_has_delay`, `flow_has_jitter` | — (mask) | Validity masks — which flow/window pairs have a meaningful label. Delay needs ≥1 packet, jitter ≥2. Passed to the model as `mask_field`. |
| `flow_total_avg_delay` | — | Delay aggregated over the whole sample rather than per window. |

### Loss and cumulative counters

| field | used by model | meaning |
|---|---|---|
| `loss_rate_per_seg` | — | Packet loss rate per temporal window. |
| `total_loss_rate` | — | Loss rate over the whole sample. |
| `flow_total_packets` | — | Total packets offered by the flow. |
| `flow_total_trans_pkts` | — | Total packets actually transmitted. Against `flow_total_packets` this gives a second, independent view of loss. |
| `flow_trans_pkts_per_seg` | — | Transmitted packets per window. |

### Scenario counts

| field | used by model | meaning |
|---|---|---|
| `num_routers`, `num_switches`, `num_traffic_generators` | — | Device counts per tier. Used by `visualization/graph_builder.classify_tiers` to infer which node ids are routers vs switches. |
| `num_r_links`, `num_s_links` | — | Link counts per tier. |
| `num_flows` | — | Flow count. |
| `sample_idx` | — | Unique sample identifier within the dataset. |

## What this gives you beyond topology and capacity

Reading the table above, the information the model does **not** consume is substantial:

- **Full delay and jitter distributions** — not just the mean, but p50/p75/p90/p95/p99 and max, for
  both metrics. `train.py` uses five of the fourteen.
- **Packet loss**, both per window (`loss_rate_per_seg`) and overall (`total_loss_rate`), plus the
  offered-vs-transmitted packet counters that let you derive it independently.
- **Tier structure** — which devices are routers vs switches, and per-tier routing/queue mappings.
  The model flattens all of this into one undifferentiated node type.
- **Millisecond-resolution packet rates** (`flow_packets_per_ms`), unique to this dataset.
- **Whole-sample aggregates** (`flow_total_*`) alongside the per-window values.

## `mawi_pcaps` vs `trex_*`

Comparing field lists against `trex_synthetic`:

- **Only in `mawi_pcaps`:** `flow_packets_per_ms`.
- **Only in `trex_*`:** `link_tg_capacity`, `link_tg_pkt_header_size`, `num_tg_links`,
  `path_to_tg_link`, `tg_groupings`, `tg_groupings_inversed`, `tg_queue_to_tg_link` — a third
  "traffic generator" device tier that `mawi_pcaps` does not have. This is why
  `graph_builder.classify_tiers` treats that tier as optional and checks whether it actually has
  members rather than merely whether the keys exist.

Note also a quirk in `models.py`: when the unified `link_capacity` is absent it concatenates only
the router and switch capacities, **silently dropping `link_tg_capacity`**. That affects `trex_*`,
not this dataset, but it is why `visualization/graph_builder.get_capacity_array` deliberately
mirrors the same behaviour rather than "fixing" it.
